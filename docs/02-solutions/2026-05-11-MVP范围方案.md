## 1. 背景

还房摇号系统当前已有较完整的业务需求、活动策划、原型页面和 MVP 技术设计，但正式工程代码尚未启动。为了避免一期建设范围过大，需要先明确 MVP 的目标、必做范围、暂缓范围和验收闭环。

本方案用于回答：一期最小可交付版本到底做什么，不做什么，以及如何判断 MVP 已经可演示、可验证、可继续迭代。

## 2. MVP 目标

MVP 目标是构建一条可演示、可验证、可审计的还房摇号核心业务闭环：

```text
导入住户 -> 导入房源 -> 录入意愿 -> 审核锁定 -> 数据封存 -> 四轮摇号 -> 发布结果 -> 住户查询 -> 导出归档
```

MVP 不追求完整平台化能力，优先证明：

1. 业务主流程可跑通。
2. 摇号过程可复现、可审计。
3. 住户、房源、意愿、结果之间的数据关系正确。
4. 现场演示链路完整。
5. 后续可以在此基础上继续扩展权限、通知、归档、现场服务等能力。

## 3. 用户角色范围

MVP 重点覆盖以下角色：

| 角色 | MVP 中的能力 |
| --- | --- |
| 项目管理员 | 查看项目状态、执行数据锁定、发布结果、归档结果 |
| 数据专员 | 导入住户、导入房源、维护意愿 |
| 审核专员 | 审核资格与意愿，确认锁定名单 |
| 摇号操作员 | 执行 A/B/C/D 四轮摇号，查看轮次结果 |
| 查询用户 | 通过参与编号和身份校验查询本人摇号结果 |

暂不重点覆盖：

- 系统管理员的完整用户/角色/菜单管理
- 监督人员独立后台视图
- 现场服务人员的签到、打印、异常登记完整流程

## 4. MVP 必做范围

### 4.1 项目基础能力

- 单项目运行，数据表保留 `project_id`。
- 初始化一个演示项目。
- 项目状态至少支持：`PREPARING`、`LOCKED`、`LOTTERY`、`FINISHED`、`ARCHIVED`。
- 项目锁定后，核心数据默认不再允许修改。

### 4.2 住户管理

- 支持 Excel 导入住户。
- 支持住户列表查询。
- 支持按参与编号、姓名、资格状态筛选。
- 支持资格状态标记：正常、取消资格、退出。
- 支持基础字段：参与编号、户主姓名、身份证号、手机号、家庭人数、资格状态、摇号状态。

### 4.3 房源管理

- 支持 Excel 导入房源。
- 支持房源列表查询。
- 支持按房型、楼栋、状态筛选。
- 支持房型 A/B/C/D。
- 支持房源状态：可用、预留、已分配。

### 4.4 意愿与审核

- 支持每户录入 1-4 个房型意愿。
- 支持按优先级排序。
- 支持审核确认。
- 支持名单锁定。
- 锁定后生成数据快照和 SHA-256 哈希。

### 4.5 摇号执行

- 支持 A/B/C/D 四轮摇号。
- 每轮按当前有效意愿筛选候选户。
- 每轮按可用房源数量确定中签数量。
- 已中签住户退出后续轮次。
- 未中签住户按下一有效志愿流转。
- 每轮保存随机种子、候选数量、中签数量、洗牌顺序和结果。
- 记录关键操作日志。

### 4.6 结果查询

- 提供公开查询接口。
- 查询条件：参与编号 + 身份信息后几位或其他简化校验方式。
- 结果发布前不展示正式结果。
- 结果发布后展示中签状态、房型、轮次、候补顺序等必要信息。
- 查询展示中必须脱敏身份证号和手机号。

### 4.7 结果导出与归档

- 支持导出摇号结果。
- 支持导出轮次结果或最终结果。
- 支持项目归档状态。
- 归档后核心数据只读。

### 4.8 原型迁移

MVP 前端优先迁移以下页面：

1. 项目工作台
2. 住户管理
3. 房源管理
4. 意愿与审核
5. 摇号控制台
6. 结果与归档
7. 住户查询页

以下页面可先保留原型或简化：

- 通知与查询管理
- 现场服务
- 大屏展示
- 项目详情/阶段总览

## 5. MVP 暂缓范围

以下内容不进入第一版 MVP，除非后续业务明确要求：

| 暂缓项 | 原因 | 后续处理 |
| --- | --- | --- |
| 真实短信发送 | 需要短信服务商、模板审核、费用和失败重试机制 | 一期用导出名单和人工通知替代 |
| 完整用户/角色/权限体系 | 建设成本较高，早期会拖慢核心闭环 | 一期只做简单管理员/操作员或临时鉴权 |
| 多项目完整切换 | MVP 先验证单项目闭环 | 表结构保留 `project_id`，后续扩展 |
| 现场签到 | 与摇号核心链路弱耦合 | 后续作为现场执行模块扩展 |
| 打印服务 | 涉及打印模板、设备和现场流程 | 后续结合现场服务建设 |
| 复杂归档流程 | 初期只需导出和只读 | 后续加入资料清单和归档审核 |
| 大屏模板管理 | MVP 只需固定展示或暂用原型 | 后续再做模板配置 |
| 外部政务系统对接 | 接口和数据边界不确定 | 后续独立立项 |
| 电子签章/缴费/票据 | 超出摇号核心范围 | 不纳入一期 |

## 6. MVP 技术边界

| 层级 | MVP 选择 |
| --- | --- |
| 后端 | Spring Boot 3 单体应用 |
| 数据访问 | MyBatis-Flex |
| 数据库 | MySQL 8.0 |
| 前端 | Vue 3 + Element Plus + Vite |
| 移动查询端 | 可独立应用，也可先作为前端公开路由 |
| 缓存 | 暂不引入 Redis |
| 鉴权 | MVP 简化处理，公开查询接口独立放行 |
| 摇号算法 | 独立 `LotteryEngine`，纯函数，可单元测试 |

## 7. 核心验收标准

### 7.1 业务闭环验收

- [ ] 可以导入一批住户。
- [ ] 可以导入一批房源。
- [ ] 可以录入或导入每户意愿。
- [ ] 可以完成审核并锁定数据。
- [ ] 锁定后可以生成数据快照哈希。
- [ ] 可以执行 A/B/C/D 四轮摇号。
- [ ] 中签住户不会重复进入后续轮次。
- [ ] 未中签住户可以按下一志愿流转。
- [ ] 可以发布结果。
- [ ] 住户可以通过公开查询页查询本人结果。
- [ ] 可以导出最终结果。
- [ ] 项目归档后核心数据只读。

### 7.2 算法验收

- [ ] 相同输入和相同种子，多次运行结果一致。
- [ ] 不同种子大概率产生不同结果。
- [ ] 中签数量等于 `min(候选户数, 可用房源数)`。
- [ ] 输出结果不出现重复住户。
- [ ] 洗牌顺序可保存，可作为候补顺序。
- [ ] 算法不依赖数据库和 Spring 容器。

### 7.3 文档验收

- [ ] MVP 范围文档已确认。
- [ ] 技术设计文档已迁移到标准目录。
- [ ] 实施计划已迁移到标准目录。
- [ ] 关键架构决策已有 ADR。
- [ ] 后续开发任务可以拆分成 GitHub Issues。

## 8. 推荐实施顺序

1. 完成文档规范和 MVP 范围确认。
2. 迁移并标准化 MVP 技术设计。
3. 迁移并标准化 MVP 实施计划。
4. 创建 GitHub Issues。
5. 初始化后端工程。
6. 优先实现 LotteryEngine 和测试。
7. 实现数据库 schema 和核心实体。
8. 实现住户、房源、意愿、锁定、摇号、查询 API。
9. 从原型迁移前端核心页面。
10. 做集成演示和阶段复盘。

## 9. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 需求范围扩大 | MVP 延期 | 坚持本文件的暂缓范围，新增需求进入后续版本 |
| 摇号公信力不足 | 影响系统可信度 | 优先实现可复现算法、哈希封存和操作日志 |
| 前端页面过多 | 分散开发精力 | 优先迁移核心闭环页面 |
| 权限设计过早复杂化 | 拖慢后端进度 | MVP 简化权限，后续再完善 |
| 数据导入格式不稳定 | 影响演示 | 先定义演示模板，后续支持更灵活导入 |

## 10. 结论

MVP 应聚焦“还房摇号核心闭环”，不是完整多项目还房平台。当前阶段最重要的是先做出一条可演示、可验证、可审计的主流程，再围绕真实使用反馈逐步扩展通知、现场、权限、归档和多项目能力。
