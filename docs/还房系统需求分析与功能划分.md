# XX还房系统需求分析与功能划分

## 一、文档说明

`文档用途`：用于梳理 XX 还房系统的产品边界、核心概念、功能模块、角色权限和建设优先级，作为后续原型设计、技术设计和开发排期的基础归档文档。  
`文档状态`：需求分析初稿。  
`适用前提`：系统面向还房业务场景，支持一个系统下管理多个还房项目，并以项目为边界组织数据、规则和活动。  
`阅读对象`：业务负责人、项目经理、产品经理、设计人员、开发人员、测试人员。

## 二、建设背景

为替代原有摇珠还房方式，并支撑后续多项目、多轮次的电子化还房活动，需要建设一套可复用、可归档、可配置、可追溯的还房系统。

结合前期已形成的活动方案，本系统不仅要解决 `摇号` 本身的问题，还要覆盖以下业务链条：

1. 项目启动与基础配置。
2. 还房户信息采集与意愿管理。
3. 房源数据管理与资格审核。
4. 电子摇号与结果发布。
5. 短信通知、二维码查询、现场执行支持。
6. 结果确认、公示复核、资料归档。

因此，本系统应当被定义为一个 `围绕“还房项目”运行的业务系统`，而不是单一的摇号工具。

## 三、产品目标

系统建设目标建议分为四类：

### 3.1 业务目标

1. 支持一个系统下管理多个还房项目。
2. 支持不同项目之间的数据、规则、活动和结果相互隔离。
3. 支持从前期准备到活动收尾的完整业务闭环。
4. 支持电子摇号替代传统摇珠，提高效率与公信力。

### 3.2 管理目标

1. 统一管理还房户、房源、意愿、摇号、通知和归档数据。
2. 支持项目全过程可视化推进。
3. 支持多人分角色协作和权限控制。

### 3.3 风控目标

1. 保证摇号规则统一、结果可追溯。
2. 保证操作留痕、关键数据可封存。
3. 保证项目间互不串数、互不误操作。

### 3.4 服务目标

1. 支持短信通知、查询二维码和现场结果查询。
2. 降低现场人工解释和查号压力。
3. 提升群众参与体验和结果获取效率。

## 四、系统定位与边界

### 4.1 系统定位

本系统定位为 `多项目还房业务管理平台`，核心职责是围绕每一个还房项目，完成项目配置、住户管理、房源管理、意愿管理、摇号执行、结果发布和归档留痕。

### 4.2 不属于本期重点范围的内容

为避免范围失控，以下内容建议暂不作为一期必做内容：

1. 财务结算、缴费和票据管理。
2. 电子签章平台深度对接。
3. 与外部政务系统的复杂双向数据交换。
4. 面向社会公众的完整小程序生态。
5. 三维选房、可视化楼盘建模等重展示功能。

## 五、核心概念设计

### 5.1 项目

`项目` 是本系统最高层级的业务对象，也是最重要的数据隔离边界。

示例：

1. `XX片区还房项目1`
2. `XX片区还房项目2`
3. `XX地块一期还房项目`

每个项目应至少包含以下基础信息：

| 字段 | 说明 |
| --- | --- |
| 项目名称 | 业务展示名称 |
| 项目编码 | 系统唯一识别编码 |
| 项目简称 | 列表和报表展示用简称 |
| 项目状态 | 草稿、准备中、报名中、锁定中、待摇号、摇号中、已结束、已归档 |
| 项目时间 | 项目启动时间、活动时间、归档时间 |
| 项目说明 | 项目背景、规则说明、备注 |
| 负责人 | 项目负责人及联系方式 |
| 适用规则 | 当前项目采用的摇号规则版本 |

### 5.2 项目级隔离要求

项目之间应实现 `业务隔离 + 数据隔离 + 权限隔离 + 展示隔离`。

| 隔离对象 | 隔离要求 |
| --- | --- |
| 住户数据 | 一个项目内的住户数据不能被其他项目直接查看和误操作 |
| 房源数据 | 房源只能归属一个项目，不允许跨项目混用 |
| 房型意愿 | 每户意愿归属于具体项目，项目切换后不得串用 |
| 摇号轮次 | 摇号轮次、结果、候补顺序均按项目独立管理 |
| 查询二维码 | 每个项目生成独立的查询入口和结果页面 |
| 短信通知 | 通知内容、通知对象、发送记录按项目独立归档 |
| 操作日志 | 所有关键操作必须能追溯到项目维度 |
| 权限授权 | 用户可在某项目有权限，在另一项目无权限 |

### 5.3 项目生命周期

建议项目按以下状态推进：

1. `草稿`：项目已创建，尚未开始录入正式数据。
2. `准备中`：规则、房源、住户等基础数据正在整理。
3. `报名中`：住户信息和房型意愿正在采集。
4. `锁定中`：审核确认，数据修正，准备封存。
5. `待摇号`：数据已锁定，等待正式摇号。
6. `摇号中`：现场或模拟摇号执行中。
7. `已结束`：摇号完成，进入确认、公示和复核阶段。
8. `已归档`：项目资料归档完成，仅允许查阅。

## 六、角色与权限设计

建议采用 `系统级角色 + 项目级授权` 的权限模式。

### 6.1 角色建议

| 角色 | 权限范围 | 说明 |
| --- | --- | --- |
| 系统管理员 | 全系统 | 负责用户、角色、参数、字典、日志和系统配置 |
| 项目管理员 | 指定项目 | 负责项目配置、规则设置、人员授权、状态推进 |
| 数据专员 | 指定项目 | 负责住户、房源、意愿、导入导出和数据修正 |
| 审核专员 | 指定项目 | 负责资格审核、异常处理、锁定确认 |
| 摇号操作员 | 指定项目 | 负责摇号执行、轮次控制、结果导出 |
| 现场服务人员 | 指定项目 | 负责签到核验、结果查询辅助、打印服务 |
| 查询用户 | 指定项目 | 仅可查询本人结果，不可进入后台 |
| 监督人员 | 指定项目 | 主要查看摇号过程、结果和日志，不直接修改数据 |

### 6.2 权限原则

1. 菜单权限按角色控制。
2. 数据权限按项目控制。
3. 关键操作需二次确认。
4. 锁定后核心数据默认只读。
5. 摇号执行、结果发布、项目归档等关键动作应具备更高权限门槛。

## 七、业务总体流程

系统整体应覆盖以下主流程：

1. 创建项目。
2. 配置项目规则、房型、轮次和时间节点。
3. 导入或录入还房户基础数据。
4. 导入或录入房源数据。
5. 采集住户房型意愿。
6. 审核住户资格和意愿有效性。
7. 锁定名单、意愿和房源。
8. 发送短信通知并生成查询二维码。
9. 进行模拟演练与正式摇号。
10. 发布摇号结果并支持查询。
11. 办理结果确认、公示复核和异常处理。
12. 导出报表、归档资料并结束项目。

## 八、功能架构划分

建议系统按 `1 个项目中心 + 8 个业务中心 + 1 个系统管理中心` 进行划分。

| 一级模块 | 模块定位 |
| --- | --- |
| 项目中心 | 管理多个还房项目及其配置边界 |
| 基础配置中心 | 配置项目规则、房型、轮次、字典、模板 |
| 住户管理中心 | 管理还房户基础信息和参与资格 |
| 房源管理中心 | 管理房源、房型和可用状态 |
| 意愿与审核中心 | 管理房型意愿、资格审核、名单锁定 |
| 摇号管理中心 | 管理轮次、试摇、正式摇号、结果生成 |
| 通知与查询中心 | 管理短信通知、二维码查询、结果展示 |
| 现场执行中心 | 管理签到、核验、打印、现场服务支持 |
| 结果与归档中心 | 管理公示、复核、确认、报表、归档 |
| 系统管理中心 | 管理用户、角色、参数、日志和安全设置 |

## 九、详细功能需求

### 9.1 项目中心

项目中心是全系统入口，应支持多项目管理。

### 主要功能

1. 新建项目。
2. 编辑项目基础信息。
3. 设置项目负责人和参与人员。
4. 切换当前操作项目。
5. 查看项目总体进度和统计概览。
6. 控制项目状态流转。
7. 项目归档与只读管理。

### 关键要求

1. 用户登录后可看到其有权限的项目列表。
2. 切换项目后，后台菜单数据自动过滤到当前项目。
3. 项目归档后默认禁止修改核心业务数据。

### 9.2 基础配置中心

该模块用于管理项目级业务规则和基础参数。

### 主要功能

1. 配置房型字典，如 A/B/C/D。
2. 配置房型数量、规则说明、展示顺序。
3. 配置摇号轮次和轮次顺序。
4. 配置意愿填报方式，如单志愿、多志愿。
5. 配置中签规则、未中签流转规则、弃选规则。
6. 配置短信模板、通知模板和公示模板。
7. 配置项目编号规则、户编号规则、房源编号规则。

### 关键要求

1. 配置项变更应保留版本。
2. 关键规则在摇号前必须锁定。
3. 规则锁定后，如需修改，应保留审批痕迹或操作日志。

### 9.3 住户管理中心

该模块负责住户档案和参与资格管理。

### 主要功能

1. 新增、编辑、删除住户信息。
2. 批量导入住户数据。
3. 管理家庭成员、证件、联系方式、代理信息。
4. 管理参与编号和资格状态。
5. 支持按姓名、编号、证件号、手机号查询。
6. 支持批量导出住户清单。

### 关键要求

1. 同一项目内应支持重复数据识别。
2. 应能标记资格异常、材料缺失、待补充等状态。
3. 应保留每次导入和修正记录。

### 9.4 房源管理中心

该模块负责房源和房型资源管理。

### 主要功能

1. 导入房源清单。
2. 管理楼栋、单元、楼层、房号、面积、朝向等字段。
3. 将房源归类到具体房型。
4. 维护房源状态，如可用、预留、锁定、已分配、禁用。
5. 查看房型数量统计和房源分布。
6. 导出房源台账。

### 关键要求

1. 一个房源只能归属一个项目。
2. 房源状态变更必须可追溯。
3. 摇号前应支持冻结房源池，防止临时变更。

### 9.5 意愿与审核中心

该模块负责房型意愿收集、资格审核、名单确认和数据锁定，是摇号前的核心环节。

### 主要功能

1. 录入住户房型意愿。
2. 支持一户多志愿顺序填写。
3. 支持批量导入房型意愿。
4. 支持意愿确认单导出。
5. 审核资格、意愿、代理材料和异常状态。
6. 生成最终参与名单。
7. 锁定住户名单、意愿数据和资格状态。

### 关键要求

1. 锁定前允许修正，锁定后原则上只读。
2. 应清晰标记每户是否具备参与资格。
3. 应支持异常记录，如资料不全、放弃参与、代理审核未通过等。

### 9.6 摇号管理中心

该模块是系统核心模块，负责试摇、正式摇号和结果生成。

### 主要功能

1. 按项目配置生成摇号轮次。
2. 支持模拟摇号或演练摇号。
3. 支持正式摇号启动、暂停、继续和结束。
4. 支持按房型建立摇号池。
5. 支持中签锁定和未中签自动流转。
6. 生成轮次结果、最终结果和候补顺序。
7. 记录摇号时间、操作人、结果摘要和日志。

### 关键要求

1. 正式摇号必须使用锁定后的数据。
2. 一户只能保留一个有效中签结果。
3. 摇号过程必须防止重复执行和误操作。
4. 正式摇号结果一旦发布，不允许后台无痕修改。

### 9.7 通知与查询中心

该模块负责信息触达和结果查询服务。

### 主要功能

1. 批量发送短信通知。
2. 管理短信发送对象、模板和状态。
3. 为项目生成统一查询二维码。
4. 提供查询页面给住户查看本人结果。
5. 支持摇号轮次结果实时更新。
6. 支持公示名单导出和查询页展示控制。

### 关键要求

1. 查询入口必须与项目绑定。
2. 查询时应进行身份校验。
3. 页面展示应脱敏处理。
4. 短信、二维码和查询记录应纳入归档。

### 9.8 现场执行中心

该模块用于活动当天的线下执行支撑。

### 主要功能

1. 签到核验。
2. 代理材料核验。
3. 现场快速查询。
4. 打印签到单、结果单、确认单。
5. 大屏展示数据接口。
6. 现场服务记录和异常登记。

### 关键要求

1. 现场功能必须简洁，操作路径尽量短。
2. 应支持快速按编号、姓名、手机号定位住户。
3. 如网络不稳定，应考虑缓存、备用打印或离线预案。

### 9.9 结果与归档中心

该模块负责项目结束后的结果管理和资料沉淀。

### 主要功能

1. 导出轮次结果表、最终结果表、候补表。
2. 管理结果公示。
3. 受理异议登记和复核记录。
4. 记录结果确认情况。
5. 归集项目资料、影像资料和日志。
6. 项目归档和历史查询。

### 关键要求

1. 归档资料应具备项目维度的完整性。
2. 已归档项目应支持查阅，不建议继续修改。
3. 报表导出格式应满足打印、公示和归档需要。

### 9.10 系统管理中心

该模块负责平台级的运行和安全。

### 主要功能

1. 用户管理。
2. 角色与权限管理。
3. 数据字典管理。
4. 系统参数管理。
5. 操作日志、登录日志查看。
6. 通知模板、打印模板维护。

### 关键要求

1. 所有关键操作必须记录日志。
2. 日志应至少包含操作人、时间、项目、动作、前后状态。
3. 应支持密码安全策略、会话管理和权限收敛。

## 十、关键业务规则

以下规则建议在系统层面固化：

1. 摇号主体按 `户` 管理，不按自然人管理。
2. 一个项目内每户只允许存在一个有效参与编号。
3. 房型意愿必须归属到具体项目。
4. 锁定后的住户名单、房型意愿、房源池应默认不可随意修改。
5. 正式摇号仅可对锁定数据执行。
6. 已中签住户自动退出后续轮次。
7. 未中签住户按有效规则进入下一志愿。
8. 查询结果应以系统正式发布结果为准。
9. 项目归档后仅允许查询和导出，不再允许正常业务编辑。

## 十一、关键数据对象

为便于后续建模，建议系统至少围绕以下对象设计：

| 对象 | 说明 |
| --- | --- |
| 项目 | 数据隔离和业务组织的顶层对象 |
| 用户 | 后台登录用户 |
| 项目成员 | 用户与项目的授权关系 |
| 住户 | 参与还房的业务主体 |
| 家庭成员 | 住户附属信息 |
| 代理信息 | 代理参与材料与状态 |
| 房源 | 可分配的具体房屋资源 |
| 房型 | 房源分类维度 |
| 房型意愿 | 住户的志愿顺序信息 |
| 审核记录 | 资格审核、异常修正、锁定记录 |
| 摇号轮次 | A/B/C/D 等具体轮次 |
| 摇号结果 | 轮次结果、最终结果、候补结果 |
| 通知记录 | 短信、公告、公示发送记录 |
| 查询记录 | 二维码访问和查询日志 |
| 归档资料 | 报表、附件、影像和操作日志 |

## 十二、非功能需求

### 12.1 安全性

1. 后台访问需要账号认证。
2. 关键数据需要操作日志和权限控制。
3. 查询页面只展示脱敏数据。
4. 项目间数据不可越权查看。

### 12.2 稳定性

1. 摇号活动期间系统需保持稳定运行。
2. 应支持数据备份和故障恢复。
3. 应支持导出关键清单以备离线应急。

### 12.3 可追溯性

1. 关键业务动作应全程留痕。
2. 数据导入、数据修正、锁定、摇号、发布、归档应可回看。

### 12.4 易用性

1. 后台应围绕项目组织菜单和数据。
2. 现场操作界面应简洁高效。
3. 查询入口应简单易懂，适配手机访问。

## 十三、一期建设建议

若按分期建设，建议一期优先建设以下能力：

1. 多项目管理。
2. 项目级权限和数据隔离。
3. 住户管理、房源管理、房型意愿管理。
4. 资格审核与锁定。
5. 分轮电子摇号。
6. 短信通知与二维码查询。
7. 结果导出、公示和归档。
8. 日志审计和基础系统管理。

## 十六、结论

本系统的核心不是简单做一个“摇号页面”，而是要建设成一个 `以项目为边界、以数据锁定为前提、以摇号为核心、以结果归档为闭环` 的完整业务系统。

在当前阶段，最应优先明确并落地的设计重点有四个：

1. `项目` 作为顶层隔离概念如何设计。
2. `住户、房源、意愿、轮次、结果` 这五类核心对象如何关联。
3. `锁定、摇号、发布、归档` 这四个关键状态如何受控。
4. `角色权限、查询服务、日志留痕` 如何保障系统可用与可信。
