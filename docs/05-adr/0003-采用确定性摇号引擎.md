# ADR-0003: 采用确定性摇号引擎

负责人：项目维护者

## 背景

还房摇号系统的核心可信度来自摇号过程的公平性、可复现性和可审计性。业务方、监督人员和住户需要相信：

- 摇号输入数据没有被篡改。
- 摇号过程遵循公开规则。
- 相同输入和相同种子可以复现相同结果。
- 结果能够被检测和审计。

如果摇号逻辑直接混在业务服务和数据库操作中，后续很难单独测试、复现和送检。

## 决策

MVP 阶段采用确定性摇号引擎。

核心设计：

1. 摇号前对锁定数据生成快照。
2. 对快照生成 SHA-256 哈希并公示。
3. 每轮摇号生成并保存随机种子。
4. 使用确定性 PRNG 和 Fisher-Yates 洗牌。
5. `LotteryEngine` 作为纯函数模块：输入候选人、数量、种子，输出排序结果和中签结果。
6. 摇号引擎不依赖数据库、不依赖 Spring 容器。

## 理由

- 可复现：同输入同种子可以得到相同结果。
- 可测试：无需启动完整应用即可单元测试。
- 可审计：可以保存输入哈希、种子、排序和结果。
- 可交付检测：可以独立提供算法代码和测试样例。
- 风险隔离：算法逻辑与数据库写入、页面展示解耦。

## 影响

### 正向影响

- 提升系统公信力。
- 降低算法逻辑被业务代码污染的风险。
- 便于编写自动化测试。
- 便于后续向监督或检测机构解释。

### 负向影响

- 需要额外设计快照、哈希和种子保存机制。
- 开发初期需要投入更多测试工作。
- 如果种子生成规则调整，需要同步更新文档和验收标准。

## 替代方案

| 方案 | 为什么没有选择 |
| --- | --- |
| 直接使用普通随机数并立即落库 | 不利于复现和审计 |
| 数据库随机排序 | 难以跨环境复现，不适合作为核心算法 |
| 手动抽签或外部工具导入结果 | 无法体现系统核心价值，也难以自动化追溯 |
