# ADR-0001: 采用标准化项目工作流

状态：Accepted
日期：2026-05-11
负责人：项目维护者
关联 Issue：N/A

## 背景

本项目当前处于早期阶段，已经产生了需求分析、活动策划、原型、技术设计和 MVP 实施计划等多类文档。随着后续进入开发，项目生命周期内还会继续产生更多方案、设计、测试、发布和复盘材料。

如果缺少统一工作流，容易出现以下问题：

- 文档类型混杂，后续难以查找。
- 需求、方案、设计、计划之间缺少追溯关系。
- 重要决策只存在于聊天或临时说明中，后续难以理解原因。
- 后续其他项目无法复用当前经验。

## 决策

本项目采用标准化项目工作流，并将其作为后续项目可复用的样板。

标准生命周期为：

```text
需求收集 -> 需求澄清 -> 方案设计 -> 技术设计 -> 任务拆分 -> 开发实现 -> 测试验收 -> 发布交付 -> 复盘归档
```

项目文档统一放在 `docs/` 下，并按生命周期拆分目录。

## 理由

- 有利于把需求、方案、设计、计划和实现关联起来。
- 有利于每周工作中的需求分析、方案设计和开发推进。
- 有利于后续通过 GitHub Issues 和 PR 建立可追踪协作流程。
- 有利于把本项目沉淀成可复制的项目管理模板。

## 影响

### 正向影响

- 项目文档结构更清晰。
- 后续新增文档有固定位置和模板。
- 决策和变更更容易追踪。
- 后续项目可以复用这套结构。

### 负向影响

- 初期需要投入时间整理文档。
- 开发前需要补齐必要的需求、方案或设计说明。
- 如果模板过重，可能增加维护负担。

## 替代方案

| 方案 | 为什么没有选择 |
| --- | --- |
| 继续沿用散放文档 | 短期简单，但长期难以维护和复用 |
| 使用重量级项目管理流程 | 当前项目早期阶段不适合过重流程 |
| 只使用 GitHub Issues 不维护文档目录 | 不利于沉淀方案、设计和决策文档 |

## 后续动作

- [ ] 将历史文档逐步迁移到标准目录。
- [ ] 将 MVP 实施计划拆分为 GitHub Issues。
- [ ] 在后续项目中复用并持续调整该工作流。
