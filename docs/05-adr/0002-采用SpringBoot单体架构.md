# ADR-0002: 采用 Spring Boot 单体架构

## 背景

还房摇号系统 MVP 的核心目标是尽快打通业务闭环，包括住户导入、房源导入、意愿审核、数据锁定、四轮摇号、结果查询和归档导出。

当前团队和项目都处于早期阶段，如果过早引入微服务、复杂网关、分布式事务和多服务部署，会显著增加开发、测试和运维成本。

## 决策

MVP 阶段采用 Spring Boot 3 单体后端架构。

后端内部按照经典分层组织：

```text
Controller -> Service -> Mapper -> Database
```

核心摇号算法独立为 `LotteryEngine` 模块，保持纯函数设计，不依赖数据库和 Spring 容器。

## 理由

- 单体架构开发和部署成本低，适合 MVP。
- 当前业务边界还在验证阶段，不适合过早拆分服务。
- 还房摇号活动更强调现场稳定性和可审计性，而不是高并发微服务扩展。
- Spring Boot + MyBatis-Plus + MySQL 技术栈成熟，适合快速交付管理类系统。
- 保留模块边界后，未来如果需要仍可拆分。

## 影响

### 正向影响

- 开发启动快。
- 本地调试简单。
- 部署链路简单。
- 数据一致性更容易保证。
- 适合先打通 MVP 闭环。

### 负向影响

- 如果后续业务规模扩大，可能需要重新拆分模块或服务。
- 单体内部边界如果不控制，容易变成强耦合代码。
- 后续多人协作时需要更严格的模块和包结构约束。

## 替代方案

| 方案 | 为什么没有选择 |
| --- | --- |
| 微服务架构 | MVP 阶段过重，增加部署和运维复杂度 |
| Serverless 架构 | 不利于现场活动可控部署和数据库事务处理 |
| 纯前端/本地工具 | 无法满足数据管理、审计、查询和归档要求 |
