## 5. 详细问题

### Q1：MVP 是否只做单项目

优先级：P0
状态：推荐待确认
来源：MVP 范围方案、技术设计、需求分析

背景：
历史需求把系统定位为多项目还房业务管理平台，但 MVP 范围方案已经收敛为先跑通单项目核心闭环，并在数据表中保留 `project_id`。

可选方案：
1. 单项目 MVP：界面上只初始化和操作一个项目，数据库保留 `project_id`。
2. 多项目 MVP：一期就做项目列表、项目切换、项目授权和项目隔离。

推荐决策：
选择方案 1。MVP 先单项目运行，所有核心表保留 `project_id`，后续再扩展多项目切换。

影响范围：
- 后端 project 表和所有业务表。
- 前端项目工作台。
- 权限模型。
- GitHub Issue 拆分。

需要你确认：
是否接受 MVP 界面上暂不做多项目切换。

### Q2：查询端身份校验方式

优先级：P0
状态：待你确认
来源：MVP 范围方案、技术设计、实施计划、需求分析

背景：
公开查询接口需要防止他人仅凭参与编号查询结果，但当前文档只写了“身份信息后几位或其他简化校验方式”，技术设计中示例为身份证后四位。

可选方案：
1. 参与编号 + 身份证后四位。
2. 参与编号 + 手机号后四位。
3. 参与编号 + 身份证后四位 + 手机号后四位。

推荐决策：
默认采用方案 1：参与编号 + 身份证后四位。若现场对隐私和误查更敏感，采用方案 3。

影响范围：
- `POST /api/query/results` 请求参数。
- 住户查询页表单。
- 住户数据导入模板。
- 隐私和安全说明。

需要你确认：
现场业务更容易使用身份证后四位、手机号后四位，还是二者组合。

### Q3：摇号结果是否绑定具体房源

优先级：P0
状态：待你确认
来源：技术设计、实施计划、需求分析

背景：
当前技术设计更偏向“按房型抽取中签资格”，但房源表是具体房源资源。如果中签后直接绑定具体房源，数据模型和摇号算法都需要增加分配逻辑。

可选方案：
1. 只抽中房型资格：结果记录中签房型、轮次、候补顺序，不绑定具体房源编号。
2. 直接分配具体房源：中签结果同时绑定 `unit_id` 或 `assigned_unit_id`。

推荐决策：
MVP 选择方案 1：只抽中房型资格，不直接绑定具体房源。具体房源分配作为后续独立流程设计。

影响范围：
- `lottery_result` 表是否需要 `unit_id`。
- 房源状态是否在摇号时变为 `ASSIGNED`。
- 结果查询展示内容。
- 摇号算法复杂度。

需要你确认：
实际还房流程中，“中签”是代表拿到某类房源资格，还是直接拿到某套房。

### Q5：PRNG 具体实现

优先级：P0
状态：待技术验证
来源：技术设计、实施计划、ADR-0003、文档迁移评估说明

背景：
历史技术设计建议使用 Java `SecureRandom.getInstance("SHA1PRNG")`。但如果要求跨 JDK、跨平台、检测机构复现，必须验证固定输入和固定种子的输出稳定性。

可选方案：
1. 使用 `SHA1PRNG`，并固定 JDK 版本和测试样本。
2. 自实现明确规范的确定性 PRNG。
3. 使用标准、可复现的第三方 PRNG 实现。

推荐决策：
暂不拍板。编码前先做一个 spike：固定候选人、固定种子，在目标 JDK 下验证输出是否稳定，并把验证结果写入测试。

影响范围：
- `LotteryEngine` 实现。
- 算法送检说明。
- 可复现性测试。
- ADR-0003 是否需要更新。

需要你确认：
项目是否有“检测机构复现”这种强要求。如果有，PRNG 选择需要更谨慎。

### Q6：字段级加密是否进入 MVP

优先级：P1
状态：待你确认
来源：技术设计、需求分析、文档迁移评估说明

背景：
文档多次提到身份证号、手机号需要加密存储和脱敏展示，但未明确加密算法、密钥管理、轮换和日志规范。

可选方案：
1. MVP 只做脱敏展示、日志禁敏、访问控制，数据库暂不字段级加密。
2. MVP 实现字段级加密，但密钥管理先采用配置文件/环境变量。
3. MVP 接入正式密钥管理方案。

推荐决策：
若 MVP 只使用演示数据或脱敏数据，采用方案 1。若会存真实身份证号和手机号，至少采用方案 2。

影响范围：
- 数据库字段类型。
- 导入、查询、筛选能力。
- 日志和审计。
- 安全测试。

需要你确认：
MVP 是否会存储真实身份证号和手机号。

### Q7：鉴权方案

优先级：P1
状态：推荐待确认
来源：MVP 范围方案、技术设计、实施计划、需求分析

背景：
MVP 暂缓完整用户/角色/权限体系，但后台 API 不能长期无鉴权。当前文档只说“简单管理员/操作员或临时鉴权”。

可选方案：
1. 开发期临时放行，正式演示前补最小鉴权。

MVP 第一阶段可先临时放行后台接口，公开查询接口独立放行；在对外演示前补一个最小管理员登录。若要更接近正式系统，优先 Session 登录。

影响范围：
- Spring Security 配置。
- 前端登录页和请求拦截。
- 后台 API 测试。

需要你确认：
MVP 是否需要对外演示登录流程。

### Q8：是否支持解锁、重摇、作废流程

优先级：P1
状态：待你确认
来源：技术设计、实施计划、需求分析

背景：
数据锁定后原则上只读；正式摇号结果一旦发布，不允许无痕修改。但现场可能存在数据错误或异常中断，需要预案。

可选方案：
1. MVP 不支持解锁/重摇/作废，只能重新初始化演示数据。
2. 支持锁定后解锁，必须写审计日志。
3. 支持作废某轮结果并重摇，必须记录作废原因、操作人、时间、旧结果和新结果。

推荐决策：
MVP 不支持无痕重摇。若业务必须支持异常预案，采用方案 3，但把流程设计为“作废 + 重新执行 + 全量审计”。

影响范围：
- 项目状态机。
- `lottery_round` 和 `lottery_result` 状态。
- 审计日志。
- 页面防误操作。

需要你确认：
现场是否存在正式摇号后发现数据错误、需要重来的业务预案。

### Q9：数据快照是否导出归档

优先级：P1
状态：推荐待确认
来源：技术设计、实施计划

背景：
当前 MVP 明确锁定后生成数据快照哈希，但是否导出完整快照文件尚未确认。

可选方案：
1. 只保存并展示 `data_hash`。
2. 保存数据库快照摘要，并支持导出 JSON/Excel 文件归档。
3. 保存完整快照文件并纳入归档资料。

推荐决策：
MVP 必做 `data_hash`。完整快照导出可作为增强项，如果强调可审计和送检，建议至少支持导出 JSON 快照。

影响范围：
- 锁定服务。
- 归档功能。
- 检测/审计材料。

需要你确认：
是否要求摇号前锁定数据可作为文件交付或送检。

## 6. 建议你优先确认的 7 个问题

为了进入开发前准备，建议你优先确认以下问题：

1. Q1：MVP 是否只做单项目。
2. Q2：查询身份校验方式。
3. Q3：摇号结果是否绑定具体房源。
4. Q4：查询端工程形态。
5. Q6：是否会存储真实身份证号和手机号。
6. Q8：是否需要解锁/重摇/作废流程。
7. Q10：大屏展示是否进入 MVP。

你可以直接按下面格式回复：

```text

Q4 同意推荐方案
Q6 会/不会存真实数据

Q10 暂用原型/做固定大屏
```
