## 1. 目的

本文用于约束第三轮历史文档迁移过程，明确“迁移不是简单复制”，而是要同时做结构整理、正确性评估和疑问标注。

## 2. 迁移原则

1. 只迁移来源文档中已有依据的内容。
2. 对明显过时、冲突或不完整的内容进行标注，不直接当作最终结论。
3. 对能基于工程常识判断的风险，写入“评估意见”或“待确认项”。
4. 对需要业务决策、现场规则或客户确认的内容，不擅自补充，统一写入“待确认问题”。
5. 标准化后的文档优先服务后续开发，不追求保留历史文档中的所有代码细节。
6. 历史文档暂不删除；标准文档确认后，再考虑在历史文档顶部标注迁移目标。

## 3. 正确性评估维度

| 维度 | 检查内容 |
| --- | --- |
| 需求一致性 | 是否与 MVP 范围方案一致，是否超出一期范围 |
| 架构合理性 | 是否符合当前项目阶段和团队成本 |
| 数据模型 | 表、字段、状态是否支撑核心业务闭环 |
| 算法可信度 | 是否可复现、可审计、可测试 |
| 安全合规 | 身份证号、手机号、公开查询接口是否有保护措施 |
| 可实施性 | 是否能按任务拆分逐步开发和验证 |
| 文档可维护性 | 是否有明确状态、关联文档、待确认问题 |

## 4. 第三轮迁移发现的主要问题

### 4.1 需要明确的技术问题

1. `SecureRandom.getInstance("SHA1PRNG")` 的跨 JDK/跨平台复现稳定性需要进一步验证。
   - 评估：如果要求严格跨环境复现，建议后续考虑自实现或明确指定可复现 PRNG。
   - 当前处理：不擅自替换算法，只在技术设计中标注待确认。

2. 敏感字段“加密存储”已有设计方向，但缺少密钥管理、加密算法和脱敏规则。
   - 评估：MVP 可先明确接口和字段，具体加密实现需要单独设计。
   - 当前处理：列为安全待确认项。

3. MVP 使用简单管理员/操作员权限，但实施计划中引入 Spring Security，缺少具体认证方案。
   - 评估：可以先保留依赖，但需要明确是临时 Basic、Session、JWT 还是开发期放行。
   - 当前处理：列为待确认项。

4. 前端是拆成 `lottery-admin` 和 `lottery-query`，还是先统一工程公开路由，需要权衡部署复杂度。
   - 评估：MVP 可先统一工程或保留独立查询端，两者都可行。
   - 当前处理：技术设计中标注推荐方向和待确认项。

### 4.2 需要明确的业务问题

1. “900 人次、700 套房源”是演示规模、目标容量还是确定业务数据量。
2. 四轮 A/B/C/D 的房型含义、房源数量、候选人进入规则是否固定。
3. 未中签流转到“下一有效志愿”的具体规则是否存在跳轮、弃选、资格变化等情况。
4. 查询身份校验到底使用身份证后四位、手机号后四位，还是二者组合。
5. 结果发布前查询端是否完全不展示，还是展示“暂未发布”。
