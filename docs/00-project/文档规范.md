# 文档规范

状态：Accepted
适用范围：本项目及后续可复用的软件项目

## 1. 文档原则

- 文档要服务决策、开发、测试和交付。
- 文档要能被后续人员独立阅读，不依赖口头上下文。
- 重要结论必须写明原因、影响和替代方案。
- 文档应该持续演进，过期文档必须标记状态。
- 同一类文档使用同一模板，降低维护成本。

## 2. 文档状态

每份正式文档顶部应包含状态字段：

- `Draft`：草稿
- `Reviewing`：评审中
- `Accepted`：已确认
- `Superseded`：已被替代
- `Archived`：归档，仅供参考

建议格式：

```markdown
状态：Draft
负责人：<姓名或角色>
最后更新：YYYY-MM-DD
关联 Issue：#<number>
```

## 3. 文件命名

普通文档：

```text
YYYY-MM-DD-中文主题-文档类型.md
```

规则：

- 日期使用文档创建日期。
- 主题和文档类型使用中文，必要时可保留英文缩写（如 MVP、API、ADR）。
- 文件名尽量简短、语义清晰，避免空格，推荐使用中文词组直接连接或使用短横线。

示例：

```text
2026-05-11-MVP范围方案.md
2026-05-11-摇号引擎技术设计.md
```

ADR：

```text
0001-中文决策标题.md
```

示例：

```text
0001-采用SpringBoot单体架构.md
```

## 4. 目录职责

- `00-project/`：长期有效的项目级规范和背景。
- `01-requirements/`：描述要解决什么问题。
- `02-solutions/`：描述可以怎么解决，以及为什么选某个方案。
- `03-designs/`：描述选定方案如何实现。
- `04-plans/`：描述如何分步骤执行。
- `05-adr/`：描述重要决策。
- `06-testing/`：描述如何验证。
- `07-releases/`：描述如何交付。
- `08-reviews/`：描述如何复盘。
- `templates/`：标准模板。
- `assets/`：文档素材。

## 5. 文档头部建议

```markdown
# 标题

状态：Draft
负责人：<角色/姓名>
最后更新：YYYY-MM-DD
关联 Issue：#<number 或 N/A>
关联文档：
- <相对路径>
```

## 6. 引用规范

- 引用项目内文档使用相对路径。
- 引用外部资料保留链接和访问日期，如必要。
- 被新文档替代的旧文档，应在顶部注明 `Superseded by: <path>`。

## 7. 变更规范

当文档影响开发或交付时，应通过 PR 修改，并在 PR 中说明：

- 修改原因
- 影响范围
- 是否需要同步修改 issue、计划或代码

## 8. 历史文档处理

已有历史文档不立即删除。整理时优先采用：

1. 在新目录建立标准版文档。
2. 在旧文档顶部标记迁移目标，或在 `docs/README.md` 中建立映射。
3. 确认没有引用后，再考虑归档或删除。
