## 2. 系统定位

还房摇号系统 MVP 定位为现场活动支撑平台，不是完整日常办公系统。系统重点服务摇号活动前、活动日和活动后短周期工作：

```text
导入住户 -> 导入房源 -> 录入意愿 -> 审核锁定 -> 数据封存 -> 四轮摇号 -> 发布结果 -> 住户查询 -> 导出归档
```

### 2.1 使用阶段

| 阶段 | 时间 | 核心动作 | 系统定位 |
| --- | --- | --- | --- |
| 活动前 | T-12 ~ T-1 | 导入住户、导入房源、采集房型意愿、审核锁定 | 数据准备工具 |
| 活动日 | T 日 | 公示数据、执行 A/B/C/D 四轮摇号、查询结果、归档封存 | 现场执行核心 |
| 活动后 | T+1 ~ T+7 | 异议处理、结果确认、资料归档 | 收尾支撑 |

### 2.2 界面范围

| 界面 | 使用者 | MVP 用途 | 迁移评估 |
| --- | --- | --- | --- |
| 操作管理端 | 工作人员 | 数据管理、意愿审核、数据锁定、执行摇号、导出归档 | MVP 必做 |
| 住户查询端 | 还房户 | 手机扫码进入，查询个人结果 | MVP 必做 |
| 大屏展示端 | 全场参会人员 | 展示摇号过程、轮次结果、统计数字 | 已确认：MVP 做固定大屏页面，不做模板管理 |

| 层级 | MVP 选择 | 说明 |
| --- | --- | --- |

| 数据访问 | MyBatis-Plus | 简化 CRUD 和分页查询 |

| 前端 | Vue 3 + Element Plus + Vite | 管理端以桌面 Web 为主 |

| 摇号算法 | 独立 `LotteryEngine` | 纯函数、可单元测试、可送检 |

## 4. 总体架构

### 4.1 架构原则

1. 单体后端优先，降低早期开发、部署和联调复杂度。
2. 前后端分离，通过 RESTful JSON API 交互。
3. 摇号核心算法独立抽离为 `LotteryEngine`，不依赖数据库和 Spring 容器。
4. 查询 API 不依赖后台登录态，但必须做身份校验、结果发布状态校验和脱敏展示。
5. 所有业务表保留 `project_id`，MVP 先单项目运行，后续再扩展多项目切换。
6. 中签结果直接绑定具体房源，摇号结果需记录分配房源并同步更新房源状态。
7. 关键动作写入操作日志，支撑追溯和归档；作废重摇必须全量审计。

### 4.2 建议工程结构

```text
housing_lottery_system/
├── lottery-server/               # Spring Boot 后端
│   ├── src/main/java/...
│   │   ├── controller/           # API 控制器
│   │   ├── service/              # 业务逻辑
│   │   ├── mapper/               # MyBatis Mapper
│   │   ├── entity/               # 数据实体
│   │   ├── engine/               # 摇号引擎，独立纯函数模块
│   │   └── config/               # 配置
│   └── src/main/resources/
├── lottery-admin/                # 管理端 + 固定大屏展示 + 公开 /query 查询路由
├── lottery-query/                # 后续可选独立住户查询端，MVP 暂不创建
```

- 已确认 MVP 先在管理端工程内提供公开 `/query` 路由，暂不创建独立 `lottery-query`；若后续查询端需要公网部署、管理端仅内网访问，再拆独立应用。

## 5. 核心业务状态

### 5.1 项目状态

建议项目状态流转：

```text
DRAFT -> PREPARING -> LOCKED -> LOTTERY -> FINISHED -> ARCHIVED
```

MVP 范围方案要求至少支持：

```text
PREPARING -> LOCKED -> LOTTERY -> FINISHED -> ARCHIVED
```

迁移评估：
- `DRAFT` 可用于初始化阶段，但不是 MVP 验收必须状态。
- 状态流转应由服务层集中校验，避免锁定后继续修改核心数据。

### 5.2 住户状态

| 状态 | 含义 |
| --- | --- |
| NORMAL | 正常参与 |
| DISQUALIFIED | 取消资格 |
| WITHDRAWN | 退出 |

### 5.3 摇号状态

历史文档建议：

```text
PENDING -> ENTERED -> WON / LOST / LOCKED
```

迁移评估：
- `LOCKED` 容易与项目锁定状态混淆，建议后续实现时明确命名，例如 `WIN_LOCKED` 或在结果表中表达“中签后不再参与”。
- 第一版可以先在 `lottery_result`、`wish.is_active` 和房源 `ASSIGNED` 状态中表达轮次参与、结果绑定和流转，避免状态过度复杂。

### 5.4 房源状态

| 状态 | 含义 |
| --- | --- |
| AVAILABLE | 可参与分配 |
| RESERVED | 预留，不参与本轮分配 |
| ASSIGNED | 已分配 |

## 6. 摇号算法设计

### 6.1 设计目标

1. 输入可验证：摇号前对锁定数据生成 SHA-256 哈希并公示。
2. 过程可复现：相同输入和相同种子，多次运行结果一致。
3. 结果可检测：算法公开、种子公开，可对样本进行统计检验。
4. 过程可审计：每轮保存种子、候选数量、中签数量、洗牌顺序和结果。

### 6.2 数据封存

摇号前生成数据快照并计算哈希：

```text
snapshot = { households, wishes, units, round_config }
data_hash = SHA-256(canonical_json(snapshot))
```

设计要求：
- 快照字段、排序规则、JSON 序列化规则必须固定，否则相同业务数据可能生成不同哈希。
- 锁定后核心数据默认不可修改。
- `data_hash` 应写入项目表或封存记录，并在现场公示。

待确认：
- 是否需要把完整快照文件导出归档。
- 是否需要在锁定后允许管理员以特殊流程解锁并重新封存。

### 6.3 种子生成

历史设计提供两种方式：

```text
MVP 简版：seed = SHA-256(data_hash + timestamp)
增强版：seed = SHA-256(data_hash + witness_input + timestamp)
```

迁移评估：
- 如果只使用服务器时间，现场可解释性较弱。
- 如果加入见证人现场输入，公平感和可监督性更强，但需要设计输入流程。
- 本文不擅自决定最终方案，建议在业务确认后写入 ADR 或更新 `0003-采用确定性摇号引擎.md`。

### 6.4 洗牌与抽取

核心算法采用 Fisher-Yates 洗牌：

```text
function drawWinners(candidates, count, rng):
  pool = candidates.copy()
  for i from pool.length - 1 down to 1:
    j = rng.nextInt(i + 1)
    swap(pool[i], pool[j])
  return pool[0:count]
```

规则：
- `count = min(候选户数, 当前房型可用房源数)`。
- 洗牌后的全量顺序需要保存，其中前 `count` 为中签，其余可作为候补顺序。
- 已中签住户退出后续轮次。
- 未中签住户按下一有效志愿流转。
- 已确认中签结果需要直接绑定具体房源：每轮在对应房型的可用房源中，按稳定排序规则取前 `winner_count` 套房源，与中签顺序一一绑定，并将房源状态改为 `ASSIGNED`。

### 6.5 PRNG 风险提示

历史设计建议使用：

```java
SecureRandom.getInstance("SHA1PRNG")
rng.setSeed(seed.getBytes())
```

迁移评估：
- `SHA1PRNG` 在 Java 环境中可用，但严格跨 JDK、跨平台复现稳定性需要验证。
- 如果“检测机构复现”是强要求，应在开发前用固定输入、固定种子在目标 JDK 上验证输出一致性。
- 后续可以考虑明确 JDK 版本，或实现一个明确规范的确定性 PRNG。

当前处理：
- MVP 设计仍保留“确定性 PRNG + Fisher-Yates”的方向。
- 具体 PRNG 实现列为待确认项，不在迁移时擅自替换。

### 6.6 LotteryEngine 约束

1. 纯函数：输入候选人列表、抽取数量、种子，输出排序结果和中签结果。
2. 不依赖数据库：计算过程只在内存中完成。
3. 不依赖 Spring 容器：单元测试可直接运行。
4. 输入、输出模型稳定：便于保存样本和送检。
5. 测试优先：核心算法必须使用 TDD 实现。

## 7. 数据库设计

### 7.1 实体关系

```text
project    1 ──── N  household
project    1 ──── N  housing_unit
project    1 ──── N  lottery_round
household  1 ──── N  wish
lottery_round 1 ──── N  lottery_result
lottery_result N ──── 1 household
```

历史文档中出现 `housing_unit N ──── 1 house_type (字典)`，但核心表未单独设计 `house_type` 字典表。

迁移评估：
- MVP 可先使用 `housing_unit.house_type` 字符串字段表达 A/B/C/D。
- 如需要可配置房型名称、面积段或排序，再增加 `house_type` 字典表。

| 字段 | 类型 | 说明 |

## 8. API 设计

### 8.1 住户 API

```text
GET    /api/households             # 列表查询，支持分页和筛选
POST   /api/households             # 新增
PUT    /api/households/{id}        # 编辑
POST   /api/households/import      # Excel 批量导入
GET    /api/households/{id}/wishes # 查看某户志愿
```

### 8.2 房源 API

```text
GET    /api/units                  # 列表查询
POST   /api/units                  # 新增
POST   /api/units/import           # Excel 批量导入
GET    /api/units/stats            # 房型统计
```

### 8.3 意愿与审核 API

```text
POST   /api/wishes                 # 录入住户志愿
GET    /api/wishes?householdId=    # 查询志愿
POST   /api/review/lock            # 锁定名单，生成 data_hash
```

建议补充：

```text
GET    /api/review/snapshot        # 查看锁定快照摘要
```

MVP 不做无痕解锁；如确需异常处理，走带审计的作废重摇流程。

### 8.4 摇号 API

```text
GET    /api/lottery/rounds                 # 轮次列表及状态
POST   /api/lottery/rounds/{id}/start      # 执行一轮摇号
POST   /api/lottery/rounds/{id}/void       # 作废某轮结果，必须提交原因并记录审计
POST   /api/lottery/rounds/{id}/redraw     # 基于作废记录重新摇号
GET    /api/lottery/results?roundId=       # 单轮结果
GET    /api/lottery/final-results          # 最终结果汇总
```

设计约束：
- 开始摇号前必须校验项目已锁定。
- 同一轮次不能重复执行；如需重摇，必须先作废旧轮次结果并记录原因、操作人、时间、旧结果和新结果。
- 每轮执行后必须保存种子、候选数量、中签数量、洗牌顺序、具体房源分配结果和审计日志。

### 8.5 公开查询 API

```text
POST   /api/query/results
Body:  { participantNo, idCardLast4 }
```

迁移评估：
- 已确认查询校验方式为“参与编号 + 身份证后四位”。
- 查询接口必须限制结果发布前展示，不能提前泄露正式结果。
- 查询结果必须脱敏展示，不返回完整身份证号和手机号。

## 10. 非功能设计

### 10.1 安全性

1. 后台 API 需要账号认证，MVP 可简化为管理员/操作员。
2. 公开查询 API 独立放行，但必须进行身份校验。
3. 身份证号、手机号需要脱敏展示。
4. MVP 先面向演示/脱敏数据，不做字段级加密；日志中禁止记录敏感字段原文。
5. 如果后续改为存储真实身份证号、手机号，需要重新确认字段级加密、密钥配置、轮换和备份方案。

### 10.2 稳定性

1. 现场摇号期间系统需保持稳定。
2. 关键清单和结果支持导出，以便离线应急。
3. 摇号执行接口应避免重复提交。
4. 关键操作失败时应返回清晰错误，并写入日志。

### 10.3 可追溯性

1. 数据锁定、摇号执行、结果发布、导出、归档均需记录审计日志。
2. 每轮摇号保存种子和洗牌顺序。
3. 数据快照哈希应可查看、可导出、可与归档文件对应。

### 10.4 公平性

1. 算法公开、实现独立、测试覆盖核心规则。
2. 数据快照哈希公示，降低事后篡改风险。
3. 轮次种子即时生成并公示。
4. 相同输入和相同种子可以复现相同结果。

## 11. 测试设计

### 11.1 单元测试重点

- `LotteryEngine` 相同输入相同种子结果一致。
- 不同种子大概率产生不同顺序。
- 中签数量等于 `min(候选户数, 可用房源数)`。
- 输出结果不出现重复住户。
- 候选户为空、抽取数量为 0、房源不足、候选少于房源等边界情况。

### 11.2 集成测试重点

- 导入住户和房源。
- 录入或导入意愿。
- 锁定数据并生成哈希。
- 执行四轮摇号。
- 中签住户不再参与后续轮次。
- 未中签住户流转到下一有效志愿。
- 发布结果后公开查询可查，发布前不可查。
- 导出最终结果。

### 11.3 TDD 要求

核心算法和业务规则应按 TDD 开发：

```text
先写失败测试 -> 运行确认失败 -> 写最小实现 -> 运行确认通过 -> 必要时重构
```
