## 1. 文档目的

本文从历史原型信息架构文档迁移而来，用于说明当前原型如何承接需求文档，并为后续前端页面迁移、MVP 页面取舍和验收演示提供依据。

历史原型定位为围绕项目运转的多项目还房业务平台 Demo，不是单一摇号页面。当前 MVP 范围有所收敛，因此本文同时标注每个页面在 MVP 中的处理方式。

## 3. 原型分析结论

### 3.1 系统定位

原型基于需求文档和活动策划方案，体现以下定位：

1. 以项目作为最高业务边界。
2. 以住户、房源、意愿、锁定、摇号、发布、归档为主流程。
3. 覆盖后台管理、现场执行、住户查询三类使用场景。

MVP 处理方式：
- 后台管理：保留核心页面。
- 住户查询：保留并优先实现。
- 现场执行：大部分暂缓，必要时仅保留入口或静态演示。

### 3.2 一期原型重点能力

历史原型优先体现：

1. 多项目切换与项目隔离。
2. 住户、房源、意愿、审核、摇号结果的关联关系。
3. `锁定 -> 摇号 -> 发布 -> 归档` 四个关键状态。
4. 住户查询页与后台发布状态同步。
5. 活动当天的现场签到、快速查询、打印占位与异常登记入口。

MVP 取舍：
- `锁定 -> 摇号 -> 发布 -> 归档` 必须保留。
- 住户、房源、意愿、结果关联关系必须保留。
- 多项目切换和完整现场执行暂缓。
- 现场签到、打印、异常登记可以作为原型保留，不进入第一轮开发。

### 3.3 核心角色视角

| 角色 | 原型体现 | MVP 处理方式 |
| --- | --- | --- |
| 项目管理员 | 切项目、看进度、控状态 | 简化为单项目状态控制 |
| 数据专员 | 维护住户、房源、意愿与审核 | MVP 必做 |
| 摇号操作员 | 执行四轮摇号并查看结果 | MVP 必做 |
| 现场服务人员 | 签到核验、快速查号、打印占位 | 暂缓或静态保留 |
| 查询用户 | 通过参与编号和身份校验查询本人结果 | MVP 必做 |

## 4. 核心对象与关键规则

### 4.1 核心对象

| 对象 | 原型用途 | MVP 处理方式 |
| --- | --- | --- |
| Project | 项目边界、状态和统计 | 简化为单项目 |
| Household | 住户台账和参与资格 | 必做 |
| Unit | 房源池和房型统计 | 必做 |
| Wish | 多志愿和流转依据 | 必做 |
| ReviewRecord | 审核、异常、锁定记录 | 简化实现 |
| LotteryRound | A/B/C/D 轮次 | 必做 |
| LotteryResult | 中签、未中签、候补顺序 | 必做 |
| NotificationRecord | 短信、发布、查询入口 | 真实短信暂缓 |
| OnsiteCheckin | 现场签到和核验 | 暂缓 |

### 4.2 关键规则

1. 摇号主体按户管理。
2. 每户按优先顺序填写 1-4 个志愿。
3. 项目未锁定时，不允许执行正式摇号。
4. 四轮摇号固定为 A/B/C/D。
5. 已中签住户自动退出后续轮次。
6. 未中签住户进入下一有效志愿对应轮次。
7. 结果未发布前，查询页不能返回正式结果。
8. 项目归档后，所有后台页面进入只读态。

迁移评估：上述规则与当前 MVP 范围一致，可作为后续页面和接口验收依据。

## 8. 推荐演示路径

MVP 演示路径建议调整为：

1. 从项目工作台进入当前项目，说明当前为单项目 MVP，但数据结构保留多项目扩展能力。
2. 进入住户管理与房源管理，展示基础数据组织方式。
3. 在意愿与审核页面完成名单/意愿锁定，展示数据哈希。
4. 进入摇号控制台执行 A/B/C/D 四轮摇号。
5. 发布结果并打开住户查询页。
6. 用住户查询页演示结果同步和脱敏展示。
7. 最后在结果与归档页面导出结果并归档，验证只读状态。

历史原型完整演示路径中的“项目详情/阶段总览、通知与查询管理、现场服务”仍可作为客户演示素材，但不建议进入 MVP 第一轮开发主路径。

## 9. 原型实现原则

历史原型实现原则：

1. 全部采用原生 HTML / CSS / JS，无需构建工具。
2. 通过 `localStorage` 共享当前项目与演示状态。
3. 不接真实后端，不发真实短信，不生成真实二维码。
4. 摇号结果使用固定种子的伪随机算法，保证每次重置后可复现。
5. 视觉上延续米白、青绿、金色系与卡片化表达。

迁移到真实 MVP 前端时的调整：
- 使用 Vue 3 + Element Plus + Vite 重建页面。
- 原型中的 `localStorage` 状态应替换为后端 API 和 Pinia 状态管理。
- 原型伪随机算法不能作为正式摇号实现；正式摇号必须调用后端 `LotteryEngine`。
- 真实短信和二维码如未纳入 MVP，应在页面上明确为暂缓或占位。

## 10. 前端迁移建议

| 顺序 | 页面 | 迁移建议 |
| --- | --- | --- |
| 1 | 项目工作台 | 建立管理端布局、菜单、项目状态卡片 |
| 2 | 住户管理 | 优先接后端住户列表、导入和筛选 API |
| 3 | 房源管理 | 接房源列表、导入和统计 API |
| 4 | 意愿与审核 | 实现锁定前校验、锁定动作和哈希展示 |
| 5 | 摇号控制台 | 接摇号轮次和执行 API，重点防误操作 |
| 6 | 结果与归档 | 实现结果查看、导出、归档只读态 |
| 7 | 住户查询页 | 移动端适配，独立路由或独立应用待确认 |
| 8 | 通知与查询管理 | 若需要，先做结果发布和查询入口展示 |
| 9 | 大屏/现场服务 | 如客户演示需要，可保留静态展示或后续迭代 |
